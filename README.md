# rmnet-driver

A macOS driver that makes a Quectel RM520N-GL 5G modem in QMI USB mode appear as an ordinary wired network port. Its protocol logic (QMI control and QMAP framing) lives in a portable, allocation-free C++ core that is tested on the host without hardware.

## Make targets

- `make test` builds `build/tests` and runs every test; `make test FILTER=bytes` runs only tests whose name contains `bytes`.
- `make driver-test` builds `build/driver-tests`, the driver's `CoreHost` (`driver/core_host.cpp`) on the host behind a fake of its USB interface (`driver/usb_port.h`), and runs its tests (`tests/driver/`); `FILTER` works as for `make test`.
- `make check-driverkit` syntax-checks every `core/src/*.cpp` against the installed DriverKit SDK, then runs `scripts/check-personalities.sh`, which checks which USB interfaces the personalities in `driver/Info.plist` may match (below, "Serial ports").
- `make script-test` runs the scripts' two test files (`tests/scripts/`): the install script's kept-app and running-driver checks (`scripts/install-checks.sh`) on saved listings, and the status classes of `scripts/soak.sh --classify` on saved status files; neither needs the network, an install or hardware.
- `make app-test` compiles and runs the app's six test programs: the status model (`app/StatusModel.swift` with `tests/app/StatusModelTests.swift`), the SMS model (`app/SmsModel.swift` with `tests/app/SmsModelTests.swift`), the AT port's answer logic (`app/AtPort.swift` with `tests/app/AtPortTests.swift`), the `Messages` tab's controller (`app/SmsController.swift` with `tests/app/SmsControllerTests.swift`, driven by a fake service) the `gps` verb's NMEA logic (`app/Nmea.swift` with `tests/app/NmeaTests.swift`) and its port reader (`app/GpsCommand.swift` with `app/Nmea.swift` and `tests/app/GpsReadTests.swift`, which reads a pseudo-terminal the test makes, never a real port); it needs no Xcode project, no window and no hardware.
- `make harness` builds `build/rmnet-harness`, the command-line harness (below).
- `make driver` generates `RMNet.xcodeproj` and builds the driver and the host app unsigned into `build/xcode/`, printing `driver build ok`.
- `make clean` removes `build/`, except `build/installed/` (the apps that can remove an installed driver, below).

## Driver

The driver is a DriverKit extension (`driver/`, bundle `io.rmnetdriver.RMNet.driver`) that links Core and presents the modem's QMI interface (USB `2c7c:0801`, interface 4) as an Ethernet port, and its interfaces 0 (DIAG) and 1 (NMEA) as serial ports (below, "Serial ports"). It is carried and installed by a host app (`app/`, `io.rmnetdriver.RMNet`) with a status window, three command-line verbs for the driver, an `sms` verb for the modem's text messages and a `gps` verb for the position from its GNSS receiver.

What the driver does: `RMNetDriver`, its network class, opens only interface 4 (after checking that its class, subclass and protocol are `0xff`), registers an Ethernet interface (`en33` on this Mac, hardware port `RM520N-GL`) with a MAC derived from the modem's serial number, and runs Core's QMI session over the control endpoints: CTL sync, the QMAP data format, then a WDS call for IPv4 and one for IPv6 on the data profile `RMNetProfile` (from the personality in `driver/Info.plist`; 1 unless set to another integer from 1 to 255). The data format asks the modem for in-band (QMAP) flow control when the personality's `RMNetFlowControl` is 1 (as `driver/Info.plist` sets it), and asks again without it if the modem does not accept it. This modem grants it, and with it an upload burst no longer holds small packets up for seconds (on one cell, two minutes apart: pings up to 0.4 s late with the request, up to 2.1 s late without; notes, "Runtime findings (in-band flow control)"). The link is reported up once both families have been tried, IPv4 then IPv6, and at least one has its settings; a family that failed is retried while the link is up (after 5 s, then backing off to 60 s). Data moves as QMAP over the bulk endpoints (32 reads posted, 8 uplink buffers; a frame that finds every uplink buffer busy is kept and offered again when one frees). Core's Ethernet emulator plays the router on the other end of the link, answering ARP, DHCP and IPv6 neighbour discovery and sending router advertisements, so macOS configures the port's addresses itself, and the modem's DNS servers reach the port. On this Mac macOS has not made the port its primary service (check with `scutil --nwi`). The driver publishes its state, the call's addresses, the profile in use and its counters as `RMNet*` registry properties, which `RMNet status` prints. The interface keeps the MTU it registered with (1500): macOS refuses `setMaxTransferUnit`, so a smaller carrier MTU reaches only IPv6 hosts, through the router advertisement. Measured on build 316.19.56 on 2026-11-14 (`docs/driverkit-notes.md`, "Runtime findings (measurements after the uplink hold and receive batching)"): a download at 16:27 carried 278 Mbit/s over its best second but was ended by its 50 MB cap 1.68 s after the start, too short to count; one four minutes later on the same instance gave 36.6 Mbit/s over 6.8 s (best second 103.8 Mbit/s), with no error or drop counter moving in either run, so the difference was not in the driver. The throughput gate is not passed (see "Done means"). The upload after the uplink hold gave 37.9 Mbit/s over 0.84 s (best second 43.2 Mbit/s) with no frame dropped for want of an uplink buffer. The first measurements (Task 7, before the uplink hold and receive batching) gave 93 to 138 Mbit/s.

- `gen.rb` writes `RMNet.xcodeproj` (not in git) with two targets: `RMNetDriver` (every `driver/*.cpp`, `driver/*.iig` and `core/src/*.cpp`) and `RMNet` (the app, which embeds the driver). Run it with `/usr/bin/ruby gen.rb` for an unsigned project, or `/usr/bin/ruby gen.rb TEAM_ID` for automatic signing with that team. It needs the `xcodeproj` gem.
- `scripts/install-driver.sh` generates the project for team `ABCDE12345`, builds it signed (letting Xcode create or update the provisioning profiles) with a bundle version derived from the current time (`<days since 2026-01-01>.<hour>.<minute>` in UTC, the form a dext version must take), copies the app to `/Applications/RMNet.app` and runs `RMNet activate`. The first activation waits for approval in System Settings, under Login Items & Extensions, Driver Extensions; later builds replace it without a new approval. A running driver does not stop when it is replaced, so a new build loads only when the modem re-enumerates (unplug it, or send `AT+CFUN=1,1`); the script says which build is running (or that it cannot tell, when it cannot read the new build's CDHash). It keeps a copy of every app that asks for activation in `build/installed/RMNet-<version>.app` (the new app right after it is copied, before it asks; the app it replaces, before removing it, if the system lists any entry with its driver version), and before copying it stops, changing nothing, if any listed driver version other than the one it replaces has no kept copy (whatever that entry's state: active, waiting for approval, switched off; an entry being uninstalled aside).
- Do not switch the driver off in System Settings while the modem is attached: the driver cannot stop, the entry is left disabled next to later builds, and the system then refuses every activation until both entries are removed.
- `scripts/driver-log.sh` follows the driver's log lines, which all start with `RMNet:`, and saves them in `build/logs/driver-<time>.log`. The system log does not keep a driver's lines, so start it before the event you want to see.
- `scripts/measure.sh <interface> down|up|down-long|up-long|both` measures throughput on one port from the port's own byte counters (`netstat -I`), with 4 parallel HTTPS transfers (8 for `both`, 4 each way) bound to the port (`--interface`, a pinned server address, proxies bypassed). It is capped: a download stops at 50,000,000 bytes or 8 s, and each of its streams also stops itself at 15,000,000 bytes; an upload stops at 10,000,000 bytes or 6 s and can send 16 MB at most. The longer modes are for the 8-second download test and a sustained upload: `down-long` stops at 320,000,000 bytes or 8 s, each stream at 90,000,000 bytes (so at most 360,000,000 bytes of payload if the watchdog dies, about 390 to 400 MB at the port); `up-long` stops at 60,000,000 bytes or 8 s and can send 80 MB of payload at most (about 83 MB at the port). `both` runs the downloads and the uploads at the same time under one watchdog, to show whether a busy uplink slows a download: four downloads, each stopping itself at 40,000,000 bytes, and four uploads of one 15,000,000-byte body each, stopped at 150,000,000 bytes in, 50,000,000 bytes out or 8 s, whichever is first (if the watchdog dies, at most about 160,000,000 bytes of payload in and 60,000,000 out); it prints the figures of the download, from the bytes in, and then of the upload, from the bytes out, from the same samples (each direction's bytes include the other direction's acknowledgements, and the labels say so), and fails, naming the side, if the four download streams delivered fewer than 1,000,000 bytes or if fewer than 1,000,000 bytes plus 3 percent of the bytes in left the port. After the stop the script waits until the port's counters settle (they move less than 100,000 bytes in 0.25 s, in both directions for `both`, at most 6 s), so the bytes still in flight, above all an upload's send buffers, are recorded. **The modem's SIM is metered**, so every run that starts its transfers, also a failed or interrupted one, appends "time direction bytes-in bytes-out" (direction `down` or `up`, also for the long modes; `both` is recorded as `down`, with its real bytes in and out) to the usage file `build/installed/measure-usage.log` (kept by `make clean`; never edit or truncate it; a missing one is created with one comment line). A run refused at its checks, or one that stops before starting its transfers, leaves no line, since it sent nothing; so does a run killed outright (SIGKILL), which may have sent data and leaves its temporary directory (with the upload body, up to 20 MB) behind. A run refuses to start (exit 2) if the recorded total plus its reservation (the stop threshold plus 10,000,000 bytes for `down` and `up`, 40,000,000 for `down-long`, 25,000,000 for `up-long`; for `both` its two thresholds plus 50,000,000, so 250,000,000) would pass 6,300,000,000 bytes, if the file has a malformed line, or if it is empty (0 bytes: it was probably emptied, and must be restored by hand). `scripts/measure.sh --analyse down|up|down-long|up-long|both <samples file>` re-prints a saved run's figures. **Its figures are double on qmi-darwin's `utun` interface:** macOS counted every packet received there twice in `netstat -I` (checked on 2026-11-15 against qmictl's own statistics, the TCP connections' byte counts and pings; notes, "Runtime findings (receive speed, and qmi-darwin's double-counted interface)"), so halve them, and the usage file over-records such a run; the script warns about it before the transfers on any interface whose name starts with `utun`. On `en33` the counters equal the driver's own. For tests without the network, `MEASURE_TEST_PORT`, `MEASURE_NETSTAT` and `MEASURE_USAGE_FILE` are accepted with the interface `lo0` only; on `lo0`, always set `MEASURE_USAGE_FILE` to a scratch copy, or the run is charged to the real usage file.
- `scripts/soak.sh <interface> <minutes>` sends light traffic bound to the port for the whole run (`ping` to 223.5.5.5 and `ping6` to 2400:3200::1, 1,000 bytes every half second each, about 8 KB a second) and every 10 seconds saves the port's byte counters, `RMNetState` and the driver's error and drop counters to `build/logs/soak-<time>.csv`. It stops early once 40,000,000 bytes have moved, after three samples in a row not `up`, or on a signal; it refuses to start if the usage file is missing, empty or malformed or if the recorded total plus 40,000,000 would pass 6,300,000,000 bytes (the ceiling `measure.sh` uses), and appends one line to the usage file once the pings have started. It ends with `soak: PASS` only if the run reached its full length, the state was `up` in every sample, every listed counter ended where it started, each ping lost at most 1 percent and no new crash report named after the driver appeared (also looked for in `Retired/`; a crash-report directory it cannot read is named and fails the verdict); otherwise `soak: FAIL` with the reasons (the full rules, the `lo0`-only test options and `--classify`, which prints the class a saved status gets, are in the script's header).
- `/Applications/RMNet.app/Contents/MacOS/RMNet activate | deactivate | status`. `status` prints whether the driver extension is installed and enabled, whether the modem is attached in QMI mode, and, if the driver is attached, its `RMNet*` registry properties. `status --json` prints the same status as one JSON object (`headline`, `advice`, `entries`, `modem`, `attached`, `bundledVersion`, `canActivate`, `canRemoveDirectly`, and the registry properties as strings under `properties`); it exits 0 also when the driver is not installed. When the system gives no listing (an error, no answer in 10 s, or a finish without a listing) it exits 1 with the headline `Unknown`, `entries` null and an `error` key; the registry part is still read. With a verb the app opens no window and exits by itself.
- `RMNet sms list [--json] | sms send <number> <text> | sms delete <index>...` reads, sends and deletes text messages over the modem's spare AT port (USB interface 3; never interface 2, the console, or 4, the driver's). The verbs take no part in the driver's installation: each opens the port (waiting up to 2 s while another program, such as the window's listing, holds it), does its work, closes the port and exits, 0 on success, 1 on a failure (printed as `sms: <sentence>`) and 2 on wrong usage (which never opens the port). Messages are read and sent in PDU mode (`AT+CMGF=0` is sent, unsaved, only if the modem is in text mode); nothing else on the modem is changed, and no message text or number is logged or written to disk. `sms list` (`AT+CMGL=4`, then `AT+CPMS?` for the store's use) prints `sms: no messages` or `sms: <n> message(s)`, followed by `, <N> of <M> stored parts used` when the modem said how full its store is; from 90 % a second line warns `sms: The modem's message store is nearly full (<N> of <M>). Delete old messages, or new ones will not arrive.` Then for each message, newest first, a line `[<stored indices>] <unread|read> <sender> <yyyy-MM-dd HH:mm:ss in the Mac's time zone, or no time>` (with ` (<k> part(s) missing)` when parts of a multi-part message are not stored) and its text with each line indented by two spaces; an entry that is not a readable SMS-DELIVER prints `[<index>] not readable`. Listing marks the listed messages as read on the modem, so a message shows `unread` on the first listing only; the window's `Messages` tab lists every 15 s while it is shown, so `sms list` in a terminal rarely shows `unread` while that tab is open, and a message first listed by the verb never shows `unread` in the window. The store holds a fixed number of entries (255 on this modem; one per part of a multi-part message), and the app never deletes by itself: when the store is full the network holds new messages, and they can expire without the owner ever seeing them, so delete old messages before it fills. Control characters in a sender or a text (other than line ends and tabs in the text) and the bidirectional controls are shown as U+FFFD, so a received message cannot rewrite the terminal or forge lines of the listing. `sms list --json` prints one JSON array of objects with `indices`, `unread`, `sender`, `time` (ISO 8601 with the zone, or null), `text`, `missingParts` and `readable`. `sms send <number> <text>` (the text is every remaining argument joined by spaces; the number is 3 to 20 digits with an optional `+`) checks the number and the length before opening the port (GSM 7-bit alphabet when every character has one, otherwise UCS-2; at most 10 parts), then sends each part with `AT+CMGS` and waits up to 60 s for the network's `+CMGS:` answer, ignoring Ctrl-C, Ctrl-Z, Ctrl-\, hang-up and SIGTERM until it has printed the result; it prints `sms: sent to <number> in <n> part(s)`. If a part fails, the rest are not sent and the sentence says how many were sent before it. When it is not known whether a part went (no answer in time, an I/O error, no `+CMGS:` line), the sentence ends `It may have been delivered; sending it again may deliver it twice.` `+CMS ERROR: 350` on a send means that on 5G standalone the modem needs IMS for SMS: `AT+QCFG="ims",1` sent on the owner's console, then a modem reboot, switches it on (a lasting modem setting, undone with `AT+QCFG="ims",0`); on this modem on 2026-11-14 sends were refused before and worked after. **Each message sent costs the SIM's owner a carrier fee.** `sms delete <index>...` deletes the given stored entries (`AT+CMGD`), the indices that `sms list` prints in brackets, each once however often it is given; a multi-part message is stored as several entries, so give all of its indices. It stops at the first failure and says how many were deleted before it (and, after no answer or an I/O error, that it is not known whether that entry was deleted); on success it prints `sms: deleted <n> stored part(s)`.
- `RMNet gps [seconds]` prints the position from the modem's GNSS receiver. It reads the NMEA sentences the modem sends on its NMEA interface (USB interface 1), which the driver presents as the serial device `/dev/cu.RM520N-GL-NMEA`; it only reads, writes nothing to the port and never changes a modem setting. It puts the port in raw mode with `CLOCAL` set, so the tty never echoes the sentences back to the modem and a change of the carrier line cannot hang the port up, and waits for data with `select(2)` (macOS's `poll(2)` does not support devices). It reads for `seconds` (a whole number from 1 to 600; 10 without one), or until one second after the first fix (the rest of that second's sentences), and the latest `RMC` or `GGA` sentence decides whether there is a fix; if the port closes or a read fails (the modem unplugged, say), it stops at once. With a fix it prints `gps: fix <latitude>, <longitude>` (degrees to six decimals, south and west negative) and, when the sentences gave them, a second line with the altitude, the number of satellites used and the time in UTC, and exits 0, also when the port closed or failed after the fix. After reading for the full time with sentences but no fix it prints `gps: no fix after <seconds> s (<n> sentences, <m> satellites in view)` and exits 1. With no sentences at all in that time it prints `gps: no NMEA sentences in <seconds> s; GNSS may be off (AT+QGPS? on the console shows it, AT+QGPS=1 switches it on)` and exits 1: the modem sends no sentences while its GNSS receiver is off, and the verb never switches it on, so `AT+QGPS=1` must be sent on the owner's console first. A port that closes or fails before the time is up, with no fix read, is reported as such and never as the receiver's state: `gps: the NMEA port closed after <n> s (<m> sentences read)` (end of file, or the port hung up), or `gps: reading the NMEA port failed after <n> s: <reason>` (waiting for or reading the port failed), with `<n>` the whole seconds since reading began; both exit 1. A port that cannot be opened prints `gps: cannot open /dev/cu.RM520N-GL-NMEA: <reason>`, and one that cannot be put in raw mode with `CLOCAL` prints `gps: cannot set up /dev/cu.RM520N-GL-NMEA: <reason>` and is closed without being read; both exit 1. Without the device it prints `gps: /dev/cu.RM520N-GL-NMEA not found (the driver is not attached to the modem's NMEA interface)` and exits 1, and wrong usage prints the usage line and exits 2; neither opens anything. The position is printed to the terminal only: nothing logs it or writes it to disk. Until a driver that presents the port is installed, the verb has been run only without the device; its reader is tested against a pseudo-terminal (`make app-test`).
- Opened with no argument (from the Finder, or `open /Applications/RMNet.app`), the app shows one window with two tabs, `Driver` and `Messages`. The `Driver` tab, refreshed every 2 seconds, shows a headline (`Not installed`, `Waiting for approval in System Settings`, `Installed, modem not attached`, `Modem is not in QMI mode`, `Connecting`, `Connected`, `Link down` or `Needs attention`; the rules are in `app/StatusModel.swift`), advice on what to do, a table of the state, the addresses, the profile, the installed driver version (`unknown` while the system's listing is unknown) and the bundled one and every counter that is not 0, and two buttons. `Install` activates the driver the app carries; with an entry listed the button reads `Update` when the app's version is newer, `Reinstall` when it is the same and `Replace` when it is older (versions compared as dotted numbers). `Install` in the window does not keep a copy of the app under `build/installed/`; `scripts/install-driver.sh` does; an update loads when the modem is next plugged in or the Mac restarts. `Install`/`Update` is off while the listing shows more than one entry, a switched-off entry or an uninstalling one (an activation then fails or adds another entry), and both buttons are off while the system's listing is unknown. `Remove…` asks for confirmation, then deactivates the driver, for which macOS asks an administrator's password. When one entry of another version is listed, it first activates the bundled version (a replacement, which needs neither approval nor password), stops unless that completes, reads the listing again and deactivates only if the listing then shows just the bundled version. When the listing is stuck it activates nothing: it deactivates the bundled version if that entry is listed and is not already being removed, and otherwise sends nothing and names the kept app (`build/installed/RMNet-<version>.app`) that can remove each listed version. A removal the system accepts is reported as accepted: the driver keeps the port until the modem is unplugged or the Mac restarts. While every listed entry is uninstalling, the window says only that, `Remove…` is off and `Install` stays off until the entry is gone. A driver switched off in System Settings while the modem is attached leaves an entry the system then refuses to replace; the window says so, and each listed version must be removed with Remove from an app that carries it (below).
- The window's `Messages` tab lists the modem's text messages with the same service as `sms list`, newest first: each row has the sender and the time (`HH:mm` for the day of the last listing, `yyyy-MM-dd HH:mm` before, in the Mac's time zone, or `no time`), the text as plain text (selectable once the row is selected, to copy a code), `unread` for a message the modem listed as unread, and `<n> part(s) missing` or `not readable` where that applies. Listing marks a message read on the modem, so the window keeps the `unread` mark itself until the message is selected or the app quits; a multi-part message whose missing part arrives later is a new entry and shows `unread` again. The list loads when the `Messages` tab is chosen and every 15 s while that tab is shown and the window can be seen (not while a delete confirmation is open); no new request goes to the modem while the `Driver` tab is shown (one already running finishes), and none at launch. `Refresh` lists at once. A line above the list says when it was last listed and how full the modem's store was then (`Updated HH:mm:ss. <N> of <M> stored parts.`, from 90 % followed by the warning `The modem's message store is nearly full (<N> of <M>). Delete old messages, or new ones will not arrive.`) or, after a failed listing (modem absent, port busy, no answer), the reason and that the list below, which stays on screen, may be out of date. `Delete…` asks for confirmation, naming the sender and the number of stored parts, and deletes every stored part of the selected message. Below the list, `To` (a number of 3 to 20 digits with an optional `+`), the text (plain text; quotes, dashes and words are never substituted as they are typed), a line saying how many parts the text needs and in which alphabet (or that it is too long: at most 10 parts), and `Send`, enabled only for a valid number and a text of 1 to 10 parts. While an input method is still composing (underlined text, such as pinyin before a candidate is chosen), `Send` is off and the line says to finish the input first; undo and redo in the text are always what `Send` sends. **Each message sent costs the SIM's owner a carrier fee.** A send can take up to a minute per part; on success the text is cleared, the number kept and the list reloaded; on failure the text is kept. Nothing is retried. The result of the last send or delete has its own line at the bottom, which a listing never changes: only the next send or delete replaces it, or typing a new message after a success clears it; a failed send's sentence says how many parts went out, and when it is not known whether a part went, that sending again may deliver it twice. One request runs at a time, off the main thread, and the buttons are off while one runs. Quitting (Cmd-Q, the Dock, closing the window, logging out) while a request to the modem runs waits until it has finished (a send is never cut short; while it waits the window, if open, says on either tab, above the tabs, `RMNet quits when the message being sent has finished.`, `...being deleted...`, or `RMNet quits when the current request to the modem has finished.` for a listing), then the app quits; with nothing running it quits at once. If the send or delete it waited for did not succeed, the quit is cancelled so that its result can be read: the app stays open, bounces its Dock icon, and the result line keeps the sentence (if the window was closed, open the window again from the app's Window menu (clicking the Dock icon should do the same; nobody has tried it); the messages and the result line are still there). The number and the text are not saved between launches, and nothing with message text or numbers is logged or written to disk.

### Removing the driver

The system deactivates a driver only when asked by an app that embeds that exact driver version. Find the active version with `systemextensionsctl list` (`io.rmnetdriver.RMNet.driver (1.0/<version>)`), then:

```sh
rm -rf /Applications/RMNet.app
ditto build/installed/RMNet-<version>.app /Applications/RMNet.app
/Applications/RMNet.app/Contents/MacOS/RMNet deactivate   # asks for an administrator's password
```

If no copy exists, build one for that version: `/usr/bin/ruby gen.rb ABCDE12345`, then the `xcodebuild` command in `scripts/install-driver.sh` with `CURRENT_PROJECT_VERSION=<version>`, and deactivate from that app the same way. Each installed entry needs its own matching app.

### Serial ports

The same driver also presents two of the modem's other USB interfaces as serial ports, with a second class, `RMNetSerial` (`driver/RMNetSerial.cpp`), which is installed, updated and removed with the rest of the driver:

| Interface | Class / subclass / protocol | Function | Device |
|---|---|---|---|
| 0 | `ff` / `ff` / `30` | DIAG | `/dev/cu.RM520N-GL-DIAG` (and `/dev/tty.RM520N-GL-DIAG`) |
| 1 | `ff` / `00` / `40` | NMEA | `/dev/cu.RM520N-GL-NMEA` (and `/dev/tty.RM520N-GL-NMEA`) |

Nothing else on the modem is claimed: interfaces 2 and 3, the AT ports, stay free for the owner's console and the app's `sms` verbs, and interface 4 is `RMNetDriver`'s. The two personalities in `driver/Info.plist` (`RMNetSerialDIAG` and `RMNetSerialNMEA`) match by interface number, which a change of the modem's USB configuration could give to another function, so `Start` refuses an interface whose class is not `0xff` or whose subclass and protocol differ from the personality's `RMNetSerialSubClass` and `RMNetSerialProtocol`, before anything is opened (the log says `RMNet: serial refused interface <n> (class <c> subclass <s> protocol <p>)`). `scripts/check-personalities.sh` refuses any personality on interface 2 or 3, a serial one on any interface but 0 or 1, `RMNetDriver` on any but 4, and a personality whose `IOUserClass` is neither of the two. Apple's `IOUserUSBSerial` moves the bytes; `RMNetSerial` names the port from the personality's `RMNetSerialName`, sends DTR and RTS to the modem when a port opens and closes, and accepts the baud rate and the other UART settings without sending them anywhere (the ports have no UART). In the I/O registry each port is an `IOUserSerial` with `IOUserClass` `RMNetSerial`.

- NMEA: `cat /dev/cu.RM520N-GL-NMEA` prints the modem's GNSS sentences. The modem sends them only while GNSS is on: `AT+QGPS=1` on the console turns it on and `AT+QGPSEND` turns it off. Without a fix the sentences come with their position fields empty.
- DIAG: the port speaks Qualcomm's DIAG protocol, framed as HDLC, for tools that take a serial device, such as QCSuper.

The `/dev/cu.*` and `/dev/tty.*` nodes are readable and writable by every local user (mode `crw-rw-rw-`, as for every serial port on macOS), so while the driver is attached any local program can read positions from the NMEA port or send DIAG commands to the modem.

**Not yet shown**: the serial ports are built but have not been installed, so none of the behaviour above has been seen on the modem yet.

## Harness

`build/rmnet-harness` runs the core against the real modem from userspace, through IOUSBHost.framework. It needs the modem attached in QMI mode (USB `2c7c:0801`; it uses only the QMI interface, the one whose class, subclass and protocol are all `0xff`) and nothing else holding that interface. It needs no root and creates no network interface.

- `rmnet-harness probe [-v]` finds the QMI interface, prints its endpoints and the modem's serial number, and exchanges one QMI CTL Sync. It prints `sync ok` and exits 0, or `sync: no answer` and exits 1 after 10 seconds. `-v` prints every QMI control message as hex, `>>` sent and `<<` received.
- `rmnet-harness connect [-v]` brings a data connection up on profile 1 with the core's connection state machine, prints `link up`, then the IPv4 address with its mask and gateway (`ipv4 none` if that family did not come up), the IPv6 address with its prefix length, the DNS servers and the MTU. It then stops the connection and exits 0. It exits 1 with `no link after 90 s` if the link does not come up. `-v` also prints every QMI message and the granted data format.
- `rmnet-harness ping [-v] [-6] [-c COUNT] ADDRESS` brings the connection up the same way, then sends COUNT ICMP echo requests (default 3), one a second, from the modem's IPv4 address (or IPv6 address with `-6`), framed as QMAP on mux `0x81` over the bulk endpoints. It answers QMAP flow-control commands from the modem and prints `reply from ADDRESS: seq=N time=T ms` for each echo reply that arrives within 2 seconds of its request. Two seconds after the last request it prints `COUNT sent, M received`, stops the connection and exits 0 if M is at least 1, 1 otherwise. It exits 1 at once if the link comes up without an address of the requested family. `-v` also prints every bulk transfer and every QMAP frame that is not a reply.

Both commands stop the connection (WDS Stop Network, then Release Client ID for every client) before exiting, also on Ctrl-C, so nothing is left running on the modem. The network takes a few seconds to finish tearing a connection down: a command started within about a second of the previous one often gets IPv6 but not IPv4 (WDS Start Network for IPv4 fails with call end reason 3GPP 36, regular deactivation). Wait a few seconds between runs.
