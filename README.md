# rmnet-driver

A macOS driver that makes a Quectel RM520N-GL 5G modem in QMI USB mode appear as an ordinary wired network port. Its protocol logic (QMI control and QMAP framing) lives in a portable, allocation-free C++ core that is tested on the host without hardware.

## Make targets

- `make test` builds `build/tests` and runs every test; `make test FILTER=bytes` runs only tests whose name contains `bytes`.
- `make check-driverkit` syntax-checks every `core/src/*.cpp` against the installed DriverKit SDK.
- `make app-test` compiles the app's status model (`app/StatusModel.swift`) with `tests/app/StatusModelTests.swift` and runs it; it needs no Xcode project and no hardware.
- `make harness` builds `build/rmnet-harness`, the command-line harness (below).
- `make driver` generates `RMNet.xcodeproj` and builds the driver and the host app unsigned into `build/xcode/`, printing `driver build ok`.
- `make clean` removes `build/`, except `build/installed/` (the apps that can remove an installed driver, below).

## Driver

The driver is a DriverKit extension (`driver/`, bundle `io.rmnetdriver.RMNet.driver`) that links Core and presents the modem's QMI interface (USB `2c7c:0801`, interface 4) as an Ethernet port. It is carried and installed by a host app (`app/`, `io.rmnetdriver.RMNet`) with a status window, three command-line verbs for the driver and an `sms` verb for the modem's text messages.

What the driver does: it opens only interface 4 (after checking that its class, subclass and protocol are `0xff`), registers an Ethernet interface (`en33` on this Mac, hardware port `RM520N-GL`) with a MAC derived from the modem's serial number, and runs Core's QMI session over the control endpoints: CTL sync, the QMAP data format, then a WDS call for IPv4 and one for IPv6 on the data profile `RMNetProfile` (from the personality in `driver/Info.plist`; 1 unless set to another integer from 1 to 255). The data format asks the modem for in-band (QMAP) flow control when the personality's `RMNetFlowControl` is 1 (as `driver/Info.plist` sets it), and asks again without it if the modem does not accept it. This modem grants it, and with it an upload burst no longer holds small packets up for seconds (on one cell, two minutes apart: pings up to 0.4 s late with the request, up to 2.1 s late without; notes, "Runtime findings (in-band flow control)"). The link is reported up once both families have been tried, IPv4 then IPv6, and at least one has its settings; a family that failed is retried while the link is up (after 5 s, then backing off to 60 s). Data moves as QMAP over the bulk endpoints (32 reads posted, 8 uplink buffers; a frame that finds every uplink buffer busy is kept and offered again when one frees). Core's Ethernet emulator plays the router on the other end of the link, answering ARP, DHCP and IPv6 neighbour discovery and sending router advertisements, so macOS configures the port's addresses itself, and the modem's DNS servers reach the port. On this Mac macOS has not made the port its primary service (check with `scutil --nwi`). The driver publishes its state, the call's addresses, the profile in use and its counters as `RMNet*` registry properties, which `RMNet status` prints. The interface keeps the MTU it registered with (1500): macOS refuses `setMaxTransferUnit`, so a smaller carrier MTU reaches only IPv6 hosts, through the router advertisement. Measured on build 316.19.56 on 2026-11-14 (`docs/driverkit-notes.md`, "Runtime findings (measurements after the uplink hold and receive batching)"): a download at 16:27 carried 278 Mbit/s over its best second but was ended by its 50 MB cap 1.68 s after the start, too short to count; one four minutes later on the same instance gave 36.6 Mbit/s over 6.8 s (best second 103.8 Mbit/s), with no error or drop counter moving in either run, so the difference was not in the driver. The throughput gate is not passed (see "Done means"). The upload after the uplink hold gave 37.9 Mbit/s over 0.84 s (best second 43.2 Mbit/s) with no frame dropped for want of an uplink buffer. The first measurements (Task 7, before the uplink hold and receive batching) gave 93 to 138 Mbit/s.

- `gen.rb` writes `RMNet.xcodeproj` (not in git) with two targets: `RMNetDriver` (every `driver/*.cpp`, `driver/*.iig` and `core/src/*.cpp`) and `RMNet` (the app, which embeds the driver). Run it with `/usr/bin/ruby gen.rb` for an unsigned project, or `/usr/bin/ruby gen.rb TEAM_ID` for automatic signing with that team. It needs the `xcodeproj` gem.
- `scripts/install-driver.sh` generates the project for team `ABCDE12345`, builds it signed (letting Xcode create or update the provisioning profiles) with a bundle version derived from the current time (`<days since 2026-01-01>.<hour>.<minute>` in UTC, the form a dext version must take), copies the app to `/Applications/RMNet.app` and runs `RMNet activate`. The first activation waits for approval in System Settings, under Login Items & Extensions, Driver Extensions; later builds replace it without a new approval. A running driver does not stop when it is replaced, so a new build loads only when the modem re-enumerates (unplug it, or send `AT+CFUN=1,1`); the script says which build is running. It keeps a copy of every app that asks for activation in `build/installed/RMNet-<version>.app` (the new app right after it is copied, before it asks; the app it replaces, before removing it, if the system lists any entry with its driver version), and it stops if the active driver has no kept copy.
- Do not switch the driver off in System Settings while the modem is attached: the driver cannot stop, the entry is left disabled next to later builds, and the system then refuses every activation until both entries are removed.
- `scripts/driver-log.sh` follows the driver's log lines, which all start with `RMNet:`, and saves them in `build/logs/driver-<time>.log`. The system log does not keep a driver's lines, so start it before the event you want to see.
- `scripts/measure.sh <interface> down|up` measures throughput on one port from the port's own byte counters (`netstat -I`), with 4 parallel HTTPS transfers bound to the port (`--interface`, a pinned server address, proxies bypassed). It is capped: a download stops at 50,000,000 bytes or 8 s, and each of its streams also stops itself at 15,000,000 bytes; an upload stops at 10,000,000 bytes or 6 s and can send 16 MB at most. **The modem's SIM is metered**, so every run that starts its transfers, also a failed or interrupted one, appends "time direction bytes-in bytes-out" to the usage file `build/installed/measure-usage.log` (kept by `make clean`; never edit or truncate it). A run refused at its checks, or one that stops before starting its transfers, leaves no line, since it sent nothing; so does a run killed outright (SIGKILL), which may have sent data. A run refuses to start (exit 2) if the recorded total plus its reservation would pass 300,000,000 bytes, or if the file has a malformed line. `scripts/measure.sh --analyse down|up <samples file>` re-prints a saved run's figures. For tests without the network, `MEASURE_TEST_PORT`, `MEASURE_NETSTAT` and `MEASURE_USAGE_FILE` are accepted with the interface `lo0` only; on `lo0`, always set `MEASURE_USAGE_FILE` to a scratch copy, or the run is charged to the real usage file.
- `scripts/soak.sh <interface> <minutes>` sends light traffic bound to the port for the whole run (`ping` to 223.5.5.5 and `ping6` to 2400:3200::1, 1,000 bytes every half second each, about 8 KB a second) and every 10 seconds saves the port's byte counters, `RMNetState` and the driver's error and drop counters to `build/logs/soak-<time>.csv`. It stops early once 40,000,000 bytes have moved, after three samples in a row not `up`, or on a signal; it refuses to start if the usage file is missing or malformed or if the recorded total plus 40,000,000 would pass its own ceiling of 400,000,000 bytes, and appends one line to the usage file once the pings have started. It ends with `soak: PASS` only if the run reached its full length, the state was `up` in every sample, every listed counter ended where it started, each ping lost at most 1 percent and no new crash report named after the driver appeared; otherwise `soak: FAIL` with the reasons (the full rules, and the `lo0`-only test options, are in the script's header).
- `/Applications/RMNet.app/Contents/MacOS/RMNet activate | deactivate | status`. `status` prints whether the driver extension is installed and enabled, whether the modem is attached in QMI mode, and, if the driver is attached, its `RMNet*` registry properties. `status --json` prints the same status as one JSON object (`headline`, `advice`, `entries`, `modem`, `attached`, `bundledVersion`, `canActivate`, `canRemoveDirectly`, and the registry properties as strings under `properties`); it exits 0 also when the driver is not installed. When the system gives no listing (an error, no answer in 10 s, or a finish without a listing) it exits 1 with the headline `Unknown`, `entries` null and an `error` key; the registry part is still read. With a verb the app opens no window and exits by itself.
- `RMNet sms list [--json] | sms send <number> <text> | sms delete <index>...` reads, sends and deletes text messages over the modem's spare AT port (USB interface 3; never interface 2, the console, or 4, the driver's). The verbs take no part in the driver's installation: each opens the port, does its work, closes the port and exits, 0 on success, 1 on a failure (printed as `sms: <sentence>`) and 2 on wrong usage (which never opens the port). Messages are read and sent in PDU mode (`AT+CMGF=0` is sent, unsaved, only if the modem is in text mode); nothing else on the modem is changed, and no message text or number is logged or written to disk. `sms list` (`AT+CMGL=4`) prints `sms: no messages` or `sms: <n> message(s)`, then for each message, newest first, a line `[<stored indices>] <unread|read> <sender> <yyyy-MM-dd HH:mm:ss in the Mac's time zone, or no time>` (with ` (<k> part(s) missing)` when parts of a multi-part message are not stored) and its text with each line indented by two spaces; an entry that is not a readable SMS-DELIVER prints `[<index>] not readable`. Listing marks the listed messages as read on the modem, so a message shows `unread` on the first listing only. Control characters in a sender or a text (other than line ends and tabs in the text) and the bidirectional controls are shown as U+FFFD, so a received message cannot rewrite the terminal or forge lines of the listing. `sms list --json` prints one JSON array of objects with `indices`, `unread`, `sender`, `time` (ISO 8601 with the zone, or null), `text`, `missingParts` and `readable`. `sms send <number> <text>` (the text is every remaining argument joined by spaces; the number is 3 to 20 digits with an optional `+`) checks the number and the length before opening the port (GSM 7-bit alphabet when every character has one, otherwise UCS-2; at most 10 parts), then sends each part with `AT+CMGS` and waits up to 60 s for the network's `+CMGS:` answer, ignoring Ctrl-C, hang-up and SIGTERM until it has printed the result; it prints `sms: sent to <number> in <n> part(s)`. If a part fails, the rest are not sent and the sentence says how many were sent before it. **Each message sent costs the SIM's owner a carrier fee.** `sms delete <index>...` deletes the given stored entries (`AT+CMGD`), the indices that `sms list` prints in brackets, each once however often it is given; a multi-part message is stored as several entries, so give all of its indices. It stops at the first failure and says how many were deleted before it (and, after no answer or an I/O error, that it is not known whether that entry was deleted); on success it prints `sms: deleted <n> stored part(s)`.
- Opened with no argument (from the Finder, or `open /Applications/RMNet.app`), the app shows one window with two tabs, `Driver` and `Messages`. The `Driver` tab, refreshed every 2 seconds, shows a headline (`Not installed`, `Waiting for approval in System Settings`, `Installed, modem not attached`, `Modem is not in QMI mode`, `Connecting`, `Connected`, `Link down` or `Needs attention`; the rules are in `app/StatusModel.swift`), advice on what to do, a table of the state, the addresses, the profile, the installed driver version (`unknown` while the system's listing is unknown) and the bundled one and every counter that is not 0, and two buttons. `Install` activates the driver the app carries; with an entry listed the button reads `Update` when the app's version is newer, `Reinstall` when it is the same and `Replace` when it is older (versions compared as dotted numbers). `Install` in the window does not keep a copy of the app under `build/installed/`; `scripts/install-driver.sh` does; an update loads when the modem is next plugged in or the Mac restarts. `Install`/`Update` is off while the listing shows more than one entry, a switched-off entry or an uninstalling one (an activation then fails or adds another entry), and both buttons are off while the system's listing is unknown. `Remove…` asks for confirmation, then deactivates the driver, for which macOS asks an administrator's password. When one entry of another version is listed, it first activates the bundled version (a replacement, which needs neither approval nor password), stops unless that completes, reads the listing again and deactivates only if the listing then shows just the bundled version. When the listing is stuck it activates nothing: it deactivates the bundled version if that entry is listed and is not already being removed, and otherwise sends nothing and names the kept app (`build/installed/RMNet-<version>.app`) that can remove each listed version. A removal the system accepts is reported as accepted: the driver keeps the port until the modem is unplugged or the Mac restarts. While every listed entry is uninstalling, the window says only that, `Remove…` is off and `Install` stays off until the entry is gone. A driver switched off in System Settings while the modem is attached leaves an entry the system then refuses to replace; the window says so, and each listed version must be removed with Remove from an app that carries it (below).
- The window's `Messages` tab lists the modem's text messages with the same service as `sms list`, newest first: each row has the sender and the time (`HH:mm` for today, `yyyy-MM-dd HH:mm` before, in the Mac's time zone, or `no time`), the text as plain text (selectable once the row is selected, to copy a code), `unread` for a message the modem listed as unread (the window keeps that mark until the message is selected or the window closes, since listing marks it read on the modem), and `<n> part(s) missing` or `not readable` where that applies. The list loads when the tab is shown and every 15 s while the tab is shown and the window can be seen; no new request goes to the modem while the `Driver` tab is shown (one already running finishes). `Refresh` lists at once. `Delete…` asks for confirmation, naming the sender and the number of stored parts, and deletes every stored part of the selected message. Below the list, `To` (a number of 3 to 20 digits with an optional `+`), the text, a line saying how many parts the text needs and in which alphabet (or that it is too long: at most 10 parts), and `Send`, enabled only for a valid number and a text of 1 to 10 parts. **Each message sent costs the SIM's owner a carrier fee.** A send can take up to a minute per part; on success the text is cleared, the number kept and the list reloaded; on failure the text is kept and the status line says how many parts went out. Nothing is retried. One request runs at a time, off the main thread, and the buttons are off while one runs. One status line shows the last result or failure; when a listing fails (modem absent, port busy, no answer) the last list stays on screen, marked as possibly out of date. The number and the text are not saved between launches, and nothing with message text or numbers is logged or written to disk.

### Removing the driver

The system deactivates a driver only when asked by an app that embeds that exact driver version. Find the active version with `systemextensionsctl list` (`io.rmnetdriver.RMNet.driver (1.0/<version>)`), then:

```sh
rm -rf /Applications/RMNet.app
ditto build/installed/RMNet-<version>.app /Applications/RMNet.app
/Applications/RMNet.app/Contents/MacOS/RMNet deactivate   # asks for an administrator's password
```

If no copy exists, build one for that version: `/usr/bin/ruby gen.rb ABCDE12345`, then the `xcodebuild` command in `scripts/install-driver.sh` with `CURRENT_PROJECT_VERSION=<version>`, and deactivate from that app the same way. Each installed entry needs its own matching app.

## Harness

`build/rmnet-harness` runs the core against the real modem from userspace, through IOUSBHost.framework. It needs the modem attached in QMI mode (USB `2c7c:0801`; it uses only the QMI interface, the one whose class, subclass and protocol are all `0xff`) and nothing else holding that interface. It needs no root and creates no network interface.

- `rmnet-harness probe [-v]` finds the QMI interface, prints its endpoints and the modem's serial number, and exchanges one QMI CTL Sync. It prints `sync ok` and exits 0, or `sync: no answer` and exits 1 after 10 seconds. `-v` prints every QMI control message as hex, `>>` sent and `<<` received.
- `rmnet-harness connect [-v]` brings a data connection up on profile 1 with the core's connection state machine, prints `link up`, then the IPv4 address with its mask and gateway (`ipv4 none` if that family did not come up), the IPv6 address with its prefix length, the DNS servers and the MTU. It then stops the connection and exits 0. It exits 1 with `no link after 90 s` if the link does not come up. `-v` also prints every QMI message and the granted data format.
- `rmnet-harness ping [-v] [-6] [-c COUNT] ADDRESS` brings the connection up the same way, then sends COUNT ICMP echo requests (default 3), one a second, from the modem's IPv4 address (or IPv6 address with `-6`), framed as QMAP on mux `0x81` over the bulk endpoints. It answers QMAP flow-control commands from the modem and prints `reply from ADDRESS: seq=N time=T ms` for each echo reply that arrives within 2 seconds of its request. Two seconds after the last request it prints `COUNT sent, M received`, stops the connection and exits 0 if M is at least 1, 1 otherwise. It exits 1 at once if the link comes up without an address of the requested family. `-v` also prints every bulk transfer and every QMAP frame that is not a reply.

Both commands stop the connection (WDS Stop Network, then Release Client ID for every client) before exiting, also on Ctrl-C, so nothing is left running on the modem. The network takes a few seconds to finish tearing a connection down: a command started within about a second of the previous one often gets IPv6 but not IPv4 (WDS Start Network for IPv4 fails with call end reason 3GPP 36, regular deactivation). Wait a few seconds between runs.
