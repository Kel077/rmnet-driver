# Reference

What the driver, the app, the scripts and the harness do, in detail: the reference behind the [README](../README.md), which says how to build, install and use them. Paths are relative to the repository root. "Notes" means `docs/driverkit-notes.md`; "this Mac" and "this modem" are the owner's, where everything recorded here was run. The evidence for each line of the design's "Done means" is in [`docs/status.md`](status.md).

## Make targets

- `make test` builds `build/tests` and runs every test; `make test FILTER=bytes` runs only tests whose name contains `bytes`.
- `make driver-test` builds `build/driver-tests`, the driver's `CoreHost` (`driver/core_host.cpp`) on the host behind a fake of its USB interface (`driver/usb_port.h`), and runs its tests (every `tests/driver/test_*.cpp`). `FILTER` works as for `make test`.
- `make check-driverkit` syntax-checks every `core/src/*.cpp` against the installed DriverKit SDK, then runs `scripts/check-personalities.sh`, which checks which USB interfaces the personalities in `driver/Info.plist` may match (below, "Serial ports" and "Supported models").
- `make script-test` runs the scripts' four test files (`tests/scripts/`): the install script's installed-app ID, kept-app and running-driver checks (`scripts/install-checks.sh`) on saved listings, the status classes of `scripts/soak.sh --classify` on saved status files, the build's team and bundle IDs (`tests/scripts/test-config.sh`: `scripts/config.sh` on `config.local` files and environment variables, in a temporary directory, and `gen.rb`'s `--team` and `--bundle-id`), and the driver's personalities (`tests/scripts/test-personalities.sh`: `driver/Info.plist` lints, the RM520N-GL's `RMNetDriver` personality prints exactly as `tests/scripts/fixtures/rmnetdriver-personality.txt`, every other `RMNetDriver` personality is a copy of it but for `idProduct` and `bInterfaceNumber`, the model lists in `scripts/check-personalities.sh`, `app/StatusModel.swift` and the plist agree, and `scripts/check-personalities.sh` passes the plist and refuses wrong ones); none needs the network, an install or hardware.
- `make app-test` compiles and runs the app's twelve test programs: the status model (`app/StatusModel.swift` with `tests/app/StatusModelTests.swift`), the SMS model (`app/SmsModel.swift` with `tests/app/SmsModelTests.swift`), the AT port's answer logic (`app/AtPort.swift` with `tests/app/AtPortTests.swift`), the `Messages` tab's controller (`app/SmsController.swift` with `tests/app/SmsControllerTests.swift`, driven by a fake service), the `gps` verb's NMEA logic (`app/Nmea.swift` with `tests/app/NmeaTests.swift`) and its port reader (`app/GpsCommand.swift` with `app/Nmea.swift` and `tests/app/GpsReadTests.swift`, which reads a pseudo-terminal the test makes, never a real port), the modem's network model (`app/ModemNetwork.swift` with `tests/app/ModemNetworkTests.swift`), its settings model (`app/ModemSettings.swift` with `app/ModemNetwork.swift` and `tests/app/ModemSettingsTests.swift`), the modem service (`app/ModemService.swift` with the AT port, SMS and modem models and `tests/app/ModemServiceTests.swift`, driven by a scripted port), the `network`, `radio`, `mode`, `apn`, `sim` and `usbmode` verbs (`app/ModemCli.swift` with the two modem models and `tests/app/ModemCliTests.swift`, driven by a fake service), the `Network` and `SIM & APN` tabs' controller (`app/ModemController.swift` with the two modem models and `tests/app/ModemControllerTests.swift`, driven by a fake service) and the quit gate (`app/QuitGate.swift` with both tabs' controllers, their models and `tests/app/QuitGateTests.swift`, which drives the real controllers on one queue with fake services); it needs no Xcode project, no window and no hardware.
- `make harness` builds `build/rmnet-harness`, the command-line harness (below).
- `make driver` generates `RMNet.xcodeproj` (with the bundle ID in `RMNET_BUNDLE_ID` when it is set in the environment or on make's command line, else `io.rmnetdriver.RMNet`; `config.local` is not read) and builds the driver and the host app unsigned into `build/xcode/`, printing `driver build ok`.
- `make clean` removes `build/`, except `build/installed/` (the apps that can remove an installed driver, below).

## Driver

The driver is a DriverKit extension (`driver/`, bundle `<the app's bundle ID>.driver`, `io.rmnetdriver.RMNet.driver` on this Mac) that links Core and presents the modem's QMI interface (USB `2c7c:0801`, interface 4; or, untested, the QMI interface of another Quectel model: below, "Supported models") as an Ethernet port, and the RM520N-GL's interfaces 0 (DIAG) and 1 (NMEA) as serial ports (below, "Serial ports"). It is carried and installed by a host app (`app/`, with the bundle ID from `config.local`, `io.rmnetdriver.RMNet` on this Mac) with a status window, three command-line verbs for the driver, an `sms` verb for the modem's text messages, a `gps` verb for the position from its GNSS receiver, `network`, `radio`, `mode`, `apn` and `sim` verbs that show and change the modem's network, radio, network mode, data profiles and SIM, and a `usbmode` verb that shows and sets the modem's USB network mode.

What the driver does: `RMNetDriver`, its network class, opens only the interface its personality names (`bInterfaceNumber`: 4 for every listed model, and 4 if the personality has no such integer), after checking that its class, subclass and protocol are `0xff` and that it has the QMI function's three endpoints, one interrupt IN, one bulk IN and one bulk OUT (otherwise a log line starting `RMNet: not the QMI interface:` says which, and nothing is opened; below, "Supported models"), and names that interface in its QMI requests; it registers an Ethernet interface (`en33` on this Mac, hardware port `RM520N-GL`) with a MAC derived from the modem's serial number, and runs Core's QMI session over the control endpoints: CTL sync, the QMAP data format, then a WDS call for IPv4 and one for IPv6 on the data profile `RMNetProfile` (from the personality in `driver/Info.plist`; 1 unless set to another integer from 1 to 255). The data format asks the modem for in-band (QMAP) flow control when the personality's `RMNetFlowControl` is 1 (as `driver/Info.plist` sets it), and asks again without it if the modem does not accept it. This modem grants it, and with it an upload burst no longer holds small packets up for seconds (on one cell, two minutes apart: pings up to 0.4 s late with the request, up to 2.1 s late without; notes, "Runtime findings (in-band flow control)"). The link is reported up once both families have been tried, IPv4 then IPv6, and at least one has its settings; a family that failed is retried while the link is up (after 5 s, then backing off to 60 s). Data moves as QMAP over the bulk endpoints (32 reads posted, 8 uplink buffers; a frame that finds every uplink buffer busy is kept and offered again when one frees). Core's Ethernet emulator plays the router on the other end of the link, answering ARP, DHCP and IPv6 neighbour discovery and sending router advertisements, so macOS configures the port's addresses itself, and the modem's DNS servers reach the port. On this Mac macOS has not made the port its primary service (check with `scutil --nwi`). The driver publishes its state, the call's addresses, the profile in use and its counters as `RMNet*` registry properties, which `RMNet status` prints. The interface keeps the MTU it registered with (1500): macOS refuses `setMaxTransferUnit`, so a smaller carrier MTU reaches only IPv6 hosts, through the router advertisement. Measured on build 316.19.56 on 2026-11-14 (`docs/driverkit-notes.md`, "Runtime findings (measurements after the uplink hold and receive batching)"): a download at 16:27 carried 278 Mbit/s over its best second but was ended by its 50 MB cap 1.68 s after the start, too short to count; one four minutes later on the same instance gave 36.6 Mbit/s over 6.8 s (best second 103.8 Mbit/s), with no error or drop counter moving in either run, so the difference was not in the driver. The throughput gate is not passed (see `docs/status.md`, "Done means"). The upload after the uplink hold gave 37.9 Mbit/s over 0.84 s (best second 43.2 Mbit/s) with no frame dropped for want of an uplink buffer. The first measurements (Task 7, before the uplink hold and receive batching) gave 93 to 138 Mbit/s.

USB idle suspend is **not supported, and was dropped on 2026-11-15**. The modem stays fully powered while the driver runs: with 32 bulk reads and the interrupt read always posted, its USB link never idles (on build 317.20.51 its `CurrentPowerState` stayed 2, on, through an idle minute). The opt-in version (the personality key `RMNetIdleSuspendMs`, commits `00e5d1e` and `3f727cf`, off as shipped) was removed, because it cannot work with a DriverKit network driver:

- For the modem to suspend, every driver attached to it must sit in its low power state (`IOUSBHostFamily.h`; `RMNetDriver` and both serial ports are direct power children of the modem's device), and the low state is the only DriverKit power state that allows it (xnu `IOUserServer.cpp`, `sPowerStates`).
- macOS's networking family switches the network interface off (`setInterfaceEnable 0`) whenever the network driver enters that low state, and on again only when it returns to full power (trial E1a, notes, "Runtime findings (idle suspend: trial E1a)"). So the modem can suspend only while `en33` is dead.
- **What it cost when it was on** (2026-11-15, build 318.1.4, the key in all three personalities): the modem suspended, `en33` disappeared, and macOS's network daemon `configd` hung; the system watchdog restarted it about every minute for three and a half hours, and the whole Mac's internet (DNS, the VPN) stayed down until the driver was removed (notes, "Runtime findings (driver features)").
- A design that might work, untested: a small USB service that alone sleeps, with the network service created outside the modem's power tree (notes, the same E1a section). The trial harness and the evidence are on branch `idle-suspend`, not on `main`.

Details are in the notes, "Changed in code, not yet on hardware (driver features)".

- `gen.rb` writes `RMNet.xcodeproj` (not in git) with two targets: `RMNetDriver` (every `driver/*.cpp`, `driver/*.iig` and `core/src/*.cpp`) and `RMNet` (the app, which embeds the driver). Run it with `/usr/bin/ruby gen.rb` for an unsigned project, or `/usr/bin/ruby gen.rb --team TEAM_ID` for automatic signing with that team; `--bundle-id BUNDLE_ID` sets the app's bundle ID (default `io.rmnetdriver.RMNet`; the driver's is `BUNDLE_ID.driver`). It needs the `xcodeproj` gem.
- `scripts/install-driver.sh` generates the project for the team and bundle ID in `config.local` (copy `config.example` and fill it in; the environment variables `RMNET_TEAM_ID` and `RMNET_BUNDLE_ID` win; it refuses before building unless both are set, and when `/Applications/RMNet.app` has another bundle ID than the configured one, since its driver would then be left with no kept app that can remove it), builds it signed (letting Xcode create or update the provisioning profiles) with a bundle version derived from the current time (`<days since 2026-01-01>.<hour>.<minute>` in UTC, the form a dext version must take), copies the app to `/Applications/RMNet.app` and runs `RMNet activate`. The first activation waits for approval in System Settings, under Login Items & Extensions, Driver Extensions; later builds replace it without a new approval. A running driver does not stop when it is replaced, so a new build loads only when the modem re-enumerates (unplug it, or send `AT+CFUN=1,1`); the script says which build is running (or that it cannot tell, when it cannot read the new build's CDHash). It keeps a copy of every app that asks for activation in `build/installed/RMNet-<version>.app` (the new app right after it is copied, before it asks; the app it replaces, before removing it, if the system lists any entry with its driver version), and before copying it stops, changing nothing, if any listed driver version other than the one it replaces has no kept copy (whatever that entry's state: active, waiting for approval, switched off; an entry being uninstalled aside).
- Do not switch the driver off in System Settings while the modem is attached: the driver cannot stop, the entry is left disabled next to later builds, and the system then refuses every activation until both entries are removed.
- `scripts/driver-log.sh` follows the driver's log lines, which all start with `RMNet:`, and saves them in `build/logs/driver-<time>.log`. The system log does not keep a driver's lines, so start it before the event you want to see.
- `scripts/measure.sh <interface> down|up|down-long|up-long|both` measures throughput on one port from the port's own byte counters (`netstat -I`), with 4 parallel HTTPS transfers (8 for `both`, 4 each way) bound to the port (`--interface`, a pinned server address, proxies bypassed). It is capped: a download stops at 50,000,000 bytes or 8 s, and each of its streams also stops itself at 15,000,000 bytes; an upload stops at 10,000,000 bytes or 6 s and can send 16 MB at most. The longer modes are for the 8-second download test and a sustained upload: `down-long` stops at 320,000,000 bytes or 8 s, each stream at 90,000,000 bytes (so at most 360,000,000 bytes of payload if the watchdog dies, about 390 to 400 MB at the port); `up-long` stops at 60,000,000 bytes or 8 s and can send 80 MB of payload at most (about 83 MB at the port). `both` runs the downloads and the uploads at the same time under one watchdog, to show whether a busy uplink slows a download: four downloads, each stopping itself at 40,000,000 bytes, and four uploads of one 15,000,000-byte body each, stopped at 150,000,000 bytes in, 50,000,000 bytes out or 8 s, whichever is first (if the watchdog dies, at most about 160,000,000 bytes of payload in and 60,000,000 out); it prints the figures of the download, from the bytes in, and then of the upload, from the bytes out, from the same samples (each direction's bytes include the other direction's acknowledgements, and the labels say so), and fails, naming the side, if the four download streams delivered fewer than 1,000,000 bytes or if fewer than 1,000,000 bytes plus 3 percent of the bytes in left the port. After the stop the script waits until the port's counters settle (they move less than 100,000 bytes in 0.25 s, in both directions for `both`, at most 6 s), so the bytes still in flight, above all an upload's send buffers, are recorded. **The modem's SIM is metered**, so every run that starts its transfers, also a failed or interrupted one, appends "time direction bytes-in bytes-out" (direction `down` or `up`, also for the long modes; `both` is recorded as `down`, with its real bytes in and out) to the usage file `build/installed/measure-usage.log` (kept by `make clean`; never edit or truncate it; a missing one is created with one comment line). A run refused at its checks, or one that stops before starting its transfers, leaves no line, since it sent nothing; so does a run killed outright (SIGKILL), which may have sent data and leaves its temporary directory (with the upload body, up to 20 MB) behind. A run refuses to start (exit 2) if the recorded total plus its reservation (the stop threshold plus 10,000,000 bytes for `down` and `up`, 40,000,000 for `down-long`, 25,000,000 for `up-long`; for `both` its two thresholds plus 50,000,000, so 250,000,000) would pass 6,300,000,000 bytes, if the file has a malformed line, or if it is empty (0 bytes: it was probably emptied, and must be restored by hand). `scripts/measure.sh --analyse down|up|down-long|up-long|both <samples file>` re-prints a saved run's figures. **Its figures are double on qmi-darwin's `utun` interface:** macOS counted every packet received there twice in `netstat -I` (checked on 2026-11-15 against qmictl's own statistics, the TCP connections' byte counts and pings; notes, "Runtime findings (receive speed, and qmi-darwin's double-counted interface)"), so halve them, and the usage file over-records such a run; the script warns about it before the transfers on any interface whose name starts with `utun`. On `en33` the counters equal the driver's own. For tests without the network, `MEASURE_TEST_PORT`, `MEASURE_NETSTAT` and `MEASURE_USAGE_FILE` are accepted with the interface `lo0` only; on `lo0`, always set `MEASURE_USAGE_FILE` to a scratch copy, or the run is charged to the real usage file.
- `scripts/soak.sh <interface> <minutes>` sends light traffic bound to the port for the whole run (`ping` to 223.5.5.5 and `ping6` to 2400:3200::1, 1,000 bytes every half second each, about 8 KB a second) and every 10 seconds saves the port's byte counters, `RMNetState` and the driver's error and drop counters to `build/logs/soak-<time>.csv`. It stops early once 40,000,000 bytes have moved, after three samples in a row not `up`, or on a signal; it refuses to start if the usage file is missing, empty or malformed or if the recorded total plus 40,000,000 would pass 6,300,000,000 bytes (the ceiling `measure.sh` uses), and appends one line to the usage file once the pings have started. It ends with `soak: PASS` only if the run reached its full length, the state was `up` in every sample, every listed counter ended where it started, each ping lost at most 1 percent and no new crash report named after the driver appeared (also looked for in `Retired/`; a crash-report directory it cannot read is named and fails the verdict); otherwise `soak: FAIL` with the reasons (the full rules, the `lo0`-only test options and `--classify`, which prints the class a saved status gets, are in the script's header).
- `/Applications/RMNet.app/Contents/MacOS/RMNet activate | deactivate | status`. `status` prints whether the driver extension is installed and enabled, which modem is attached and whether it is in QMI mode (for example `modem: 2c7c:0801 RM520N-GL attached, QMI interface 4 (class, subclass, protocol ff)`; another model from "Supported models" has `(untested)` after its name, and with none attached the line lists the products looked for), and, if the driver is attached, its `RMNet*` registry properties. `status --json` prints the same status as one JSON object (`headline`, `advice`, `entries`, `modem`, `attached`, `bundledVersion`, `canActivate`, `canRemoveDirectly`, and the registry properties as strings under `properties`); it exits 0 also when the driver is not installed. When the system gives no listing (an error, no answer in 10 s, or a finish without a listing) it exits 1 with the headline `Unknown`, `entries` null and an `error` key; the registry part is still read. With a verb the app opens no window and exits by itself.
- `RMNet sms list [--json] | sms send <number> <text> | sms delete <index>...` reads, sends and deletes text messages over the modem's spare AT port (USB interface 3; never interface 2, the console, or 4, the driver's). The verbs take no part in the driver's installation: each opens the port (waiting up to 2 s while another program, such as the window's listing, holds it), does its work, closes the port and exits, 0 on success, 1 on a failure (printed as `sms: <sentence>`) and 2 on wrong usage (which never opens the port). Messages are read and sent in PDU mode (`AT+CMGF=0` is sent, unsaved, only if the modem is in text mode); nothing else on the modem is changed, and no message text or number is logged or written to disk. `sms list` (`AT+CMGL=4`, then `AT+CPMS?` for the store's use) prints `sms: no messages` or `sms: <n> message(s)`, followed by `, <N> of <M> stored parts used` when the modem said how full its store is; from 90 % a second line warns `sms: The modem's message store is nearly full (<N> of <M>). Delete old messages, or new ones will not arrive.` Then for each message, newest first, a line `[<stored indices>] <unread|read> <sender> <yyyy-MM-dd HH:mm:ss in the Mac's time zone, or no time>` (with ` (<k> part(s) missing)` when parts of a multi-part message are not stored) and its text with each line indented by two spaces; an entry that is not a readable SMS-DELIVER prints `[<index>] not readable`. Listing marks the listed messages as read on the modem, so a message shows `unread` on the first listing only; the window's `Messages` tab lists every 15 s while it is shown, so `sms list` in a terminal rarely shows `unread` while that tab is open, and a message first listed by the verb never shows `unread` in the window. The store holds a fixed number of entries (255 on this modem; one per part of a multi-part message), and the app never deletes by itself: when the store is full the network holds new messages, and they can expire without the owner ever seeing them, so delete old messages before it fills. Control characters in a sender or a text (other than line ends and tabs in the text) and the bidirectional controls are shown as U+FFFD, so a received message cannot rewrite the terminal or forge lines of the listing. `sms list --json` prints one JSON array of objects with `indices`, `unread`, `sender`, `time` (ISO 8601 with the zone, or null), `text`, `missingParts` and `readable`. `sms send <number> <text>` (the text is every remaining argument joined by spaces; the number is 3 to 20 digits with an optional `+`) checks the number and the length before opening the port (GSM 7-bit alphabet when every character has one, otherwise UCS-2; at most 10 parts), then sends each part with `AT+CMGS` and waits up to 60 s for the network's `+CMGS:` answer, ignoring Ctrl-C, Ctrl-Z, Ctrl-\, hang-up and SIGTERM until it has printed the result; it prints `sms: sent to <number> in <n> part(s)`. If a part fails, the rest are not sent and the sentence says how many were sent before it. When it is not known whether a part went (no answer in time, an I/O error, no `+CMGS:` line), the sentence ends `It may have been delivered; sending it again may deliver it twice.` `+CMS ERROR: 350` on a send means that on 5G standalone the modem needs IMS for SMS: `AT+QCFG="ims",1` sent on the owner's console, then a modem reboot, switches it on (a lasting modem setting, undone with `AT+QCFG="ims",0`); on this modem on 2026-11-14 sends were refused before and worked after. **Each message sent costs the SIM's owner a carrier fee.** `sms delete <index>...` deletes the given stored entries (`AT+CMGD`), the indices that `sms list` prints in brackets, each once however often it is given; a multi-part message is stored as several entries, so give all of its indices. It stops at the first failure and says how many were deleted before it (and, after no answer or an I/O error, that it is not known whether that entry was deleted); on success it prints `sms: deleted <n> stored part(s)`.
- `RMNet gps [seconds]` prints the position from the modem's GNSS receiver. It reads the NMEA sentences the modem sends on its NMEA interface (USB interface 1), which the driver presents as the serial device `/dev/cu.RM520N-GL-NMEA`; it only reads, writes nothing to the port and never changes a modem setting. It puts the port in raw mode with `CLOCAL` set, so the tty never echoes the sentences back to the modem and a change of the carrier line cannot hang the port up, and waits for data with `select(2)` (macOS's `poll(2)` does not support devices). It reads for `seconds` (a whole number from 1 to 600; 10 without one), or until one second after the first fix (the rest of that second's sentences), and the latest `RMC` or `GGA` sentence decides whether there is a fix; if the port closes or a read fails (the modem unplugged, say), it stops at once. With a fix it prints `gps: fix <latitude>, <longitude>` (degrees to six decimals, south and west negative) and, when the sentences gave them, a second line with the altitude, the number of satellites used and the time in UTC, and exits 0, also when the port closed or failed after the fix. When the time runs out with sentences but no fix (also when a fix was read and then lost within the second after it) it prints `gps: no fix after <seconds> s (<n> sentences, <m> satellites in view)` and exits 1. With no sentences at all in that time it prints `gps: no NMEA sentences in <seconds> s; GNSS may be off (AT+QGPS? on the console shows it, AT+QGPS=1 switches it on)` and exits 1: the modem sends no sentences while its GNSS receiver is off, and the verb never switches it on, so `AT+QGPS=1` must be sent on the owner's console first. A port that closes or fails before the time is up, with no fix read, is reported as such and never as the receiver's state: `gps: the NMEA port closed after <n> s (<m> sentences read)` (end of file, or the port hung up), or `gps: reading the NMEA port failed after <n> s: <reason>` (waiting for or reading the port failed), with `<n>` the whole seconds since reading began; both exit 1. A port that cannot be opened prints `gps: cannot open /dev/cu.RM520N-GL-NMEA: <reason>`, and one that cannot be put in raw mode with `CLOCAL` prints `gps: cannot set up /dev/cu.RM520N-GL-NMEA: <reason>` and is closed without being read; both exit 1. Without the device it prints `gps: /dev/cu.RM520N-GL-NMEA not found (the driver is not attached to the modem's NMEA interface)` and exits 1, and wrong usage prints the usage line and exits 2; neither opens anything. The position is printed to the terminal only: nothing logs it or writes it to disk. Only one program should read the port at a time: two readers split the bytes between them, and each sees broken sentences. The first read after an open can return a few seconds of sentences the modem sent before it. Its reader is tested against a pseudo-terminal (`make app-test`), and it was run on the modem on 2026-11-15 (below, "Serial ports").
- `RMNet network [--json] | radio [on|off] | mode [auto|nr5g|lte|lte:nr5g|…] | apn [show] [--json] | apn set [--apn <name>] [--type ipv4|ipv6|ipv4v6] [--user <name>] [--password | --no-password] [--auth none|pap|chap|pap-or-chap] [--no-redial] | sim [--json] | sim unlock [--last-attempt]` show and change the modem's network and settings over the same spare AT port as the `sms` verbs (USB interface 3; never interface 2 or 4), in the same way: each request opens the port (waiting up to 2 s while another program holds it), sends its commands one at a time (3 s for each read), closes the port, and the verb exits 0 on success, 1 on a failure (printed as one line `<verb>: <sentence>`) and 2 on wrong usage (which never opens the port: also a mode, `--type` or `--auth` value it does not know, an option given twice, `--password` with `--no-password`, `apn set` with nothing to set, or anything after `sim unlock` but `--last-attempt`). Nothing sent or read is logged. `network` sends `AT+CFUN?`, `AT+COPS?`, `AT+QSPN`, `AT+C5GREG?`, `AT+CEREG?`, `AT+CGREG?`, `AT+CREG?`, `AT+QENG="servingcell"`, `AT+QCAINFO`, `AT+QNWPREFCFG="mode_pref"` and `AT+QNWPREFCFG="nr5g_disable_mode"` and prints one line `<name>: <value>` for each of registration, operator (with the network's own name and the PLMN), technology, band (`(carrier aggregation)` when two carriers of one RAT are aggregated), signal (RSRP, RSRQ, SINR), cell (PCI, cell ID, TAC), channel (ARFCN, EARFCN or UARFCN, and the bandwidth), connection (`idle`, `connected`, `searching` or `limited service`), radio and network mode, such as `signal: RSRP -92 dBm, RSRQ -11 dB, SINR 11 dB`; on EN-DC (5G NSA) the signal, cell and channel lines come once a leg, `signal (lte):` and `signal (5g):`. A value the modem did not give is left out, and a query it refuses only leaves its part out. `network --json` prints one JSON object (`radio`, `registration`, `roaming`, `operator`, `networkName`, `plmn`, `technology`, `state`, `cells`, `carriers`, `mode`, `nr5gDisableMode`; a value not read is null). `radio` (the same reads) prints `radio: on`, `radio: off (airplane mode)`, `radio: minimum functionality` or `radio: AT+CFUN <n>`. `radio off` sends `AT+CFUN=4` (airplane mode; up to 20 s) and prints `radio: The radio is off. The driver's connection is down until the radio is switched on again.`: **the modem then has no network, and the driver no connection, until `RMNet radio on`.** `radio on` sends `AT+CFUN=1`, then reads the registration (`AT+C5GREG?`, `AT+CEREG?`, `AT+CGREG?`, `AT+CREG?`) every second for up to 30 s, and prints `radio: The radio is on; registered, home network (5GS) after <n> s.`, or that the modem has not registered yet (still exit 0: the radio is on). `mode` (the same reads) prints `mode: <mode> (<in words>)`, such as `mode: AUTO (automatic (5G, LTE and WCDMA))`; the same RATs in any order read the same, so the modem's `NR5G:LTE` is `5G and LTE`. `mode <m>` (`auto`, or one or more of `wcdma`, `lte` and `nr5g` joined by `:`, each at most once, in any case) reads `AT+QNWPREFCFG="mode_pref"`, sends `AT+QNWPREFCFG="mode_pref",<M>` (upper-cased, the RATs in the order typed; ### Removing the driver

The system deactivates a driver only when asked by an app that embeds that exact driver version. Find the active version with `systemextensionsctl list` (`<bundle ID>.driver (1.0/<version>)`), then:

```sh
rm -rf /Applications/RMNet.app
ditto build/installed/RMNet-<version>.app /Applications/RMNet.app
/Applications/RMNet.app/Contents/MacOS/RMNet deactivate   # asks for an administrator's password
```

If no copy exists, build one for that version: `/usr/bin/ruby gen.rb --team <your team ID> --bundle-id <your bundle ID>`, then the `xcodebuild` command in `scripts/install-driver.sh` with `CURRENT_PROJECT_VERSION=<version>`, and deactivate from that app the same way. Each installed entry needs its own matching app.

To change the bundle ID (`RMNET_BUNDLE_ID`), remove the driver under the old ID first, with `Remove…` in the window or as above. Neither deletes the app, and `scripts/install-driver.sh` refuses while `/Applications/RMNet.app` has another bundle ID than the configured one, whether or not its driver is still listed. So once `systemextensionsctl list` shows no entry for the old `<bundle ID>.driver`, or only one being uninstalled, delete the app (`rm -rf /Applications/RMNet.app`), then change `config.local` and run the script.

### Serial ports

The same driver also presents two of the modem's other USB interfaces as serial ports, with a second class, `RMNetSerial` (`driver/RMNetSerial.cpp`), which is installed, updated and removed with the rest of the driver:

| Interface | Class / subclass / protocol | Function | Device |
|---|---|---|---|
| 0 | `ff` / `ff` / `30` | DIAG | `/dev/cu.RM520N-GL-DIAG` (and `/dev/tty.RM520N-GL-DIAG`) |
| 1 | `ff` / `00` / `40` | NMEA | `/dev/cu.RM520N-GL-NMEA` (and `/dev/tty.RM520N-GL-NMEA`) |

Nothing else on the modem is claimed: interfaces 2 and 3, the AT ports, stay free for the owner's console (interface 2) and the app (interface 3: the `sms`, `network`, `radio`, `mode`, `apn`, `sim` and `usbmode` verbs and the window's tabs that talk to the modem), and interface 4 is `RMNetDriver`'s. The two personalities in `driver/Info.plist` (`RMNetSerialDIAG` and `RMNetSerialNMEA`) match by interface number, which a change of the modem's USB configuration could give to another function, so `Start` refuses an interface whose class is not `0xff` or whose subclass and protocol differ from the personality's `RMNetSerialSubClass` and `RMNetSerialProtocol`, before anything is opened (the log says `RMNet: serial refused interface <n> (class <c> subclass <s> protocol <p>)`). `scripts/check-personalities.sh` refuses any personality on interface 2 or 3 (except `RMNetDriver` for another model in its list, which may match only that model's QMI interface: below, "Supported models"), a serial one for any product but `0x0801` or on any interface but 0 or 1, `RMNetDriver` for the RM520N-GL on any interface but 4, `RMNetDriver` for a product not in its list, and a personality whose `IOUserClass` is neither of the two. Apple's `IOUserUSBSerial` moves the bytes; `RMNetSerial` names the port from the personality's `RMNetSerialName`, sends DTR and RTS to the modem when a port opens and closes, and accepts the baud rate and the other UART settings without sending them anywhere (the ports have no UART). In the I/O registry each port is an `IOUserSerial` with `IOUserClass` `RMNetSerial`.

- NMEA: `cat /dev/cu.RM520N-GL-NMEA` prints the modem's GNSS sentences. The modem sends them only while GNSS is on: `AT+QGPS=1` on the console turns it on and `AT+QGPSEND` turns it off. Without a fix the sentences come with their position fields empty.
- DIAG: the port speaks Qualcomm's DIAG protocol, framed as HDLC, for tools that take a serial device, such as QCSuper.

The `/dev/cu.*` and `/dev/tty.*` nodes are readable and writable by every local user (mode `crw-rw-rw-`, as for every serial port on macOS), so while the driver is attached any local program can read positions from the NMEA port or send DIAG commands to the modem.

**Shown on the modem** (build 317.20.51, 2026-11-15 04:50 to 04:56; notes, "Runtime findings (serial ports)"): after the install and one modem reboot, `RMNetSerial` was attached to interfaces 0 and 1, `RMNetDriver` to 4, and interfaces 2 and 3 had no driver; the devices were `/dev/cu.RM520N-GL-DIAG` and `/dev/cu.RM520N-GL-NMEA` (and their `tty.` twins); each of the three driver instances ran in its own process; `en33` had its IPv4 and IPv6 addresses, pings answered 3 of 3 in each family, `sms list` and the owner's console worked. With GNSS switched on, the NMEA port delivered `GGA`, `GSA`, `RMC` and `VTG` once a second (no fix and no satellites in view on that run, so the position fields were empty), and `RMNet gps 20` printed `gps: no fix after 20 s (104 sentences, 0 satellites in view)`. The DIAG port answered the version request (`00 78 F0 7E`) with a 58-byte HDLC frame. A modem reboot with the NMEA port open ended the readers with `Device not configured` (`RMNet gps` printed `gps: reading the NMEA port failed after 9 s: Device not configured`), the instances stopped cleanly, and the ports, `en33`, SMS and the console came back. A fix has not been seen; whether an antenna is attached is not known.

### Supported models

`RMNetDriver` has one personality per model in `driver/Info.plist`: `RMNetDriver` for the RM520N-GL, and `RMNetDriver_<idProduct in hex>` for each other model, a copy of it but for `idProduct` and `bInterfaceNumber`. Each names one product of vendor `0x2c7c` (Quectel) and the number of its QMI interface. In the modem's QMI USB configuration (`AT+QCFG="usbnet",0`) that number is the QMI function's, so the personality alone keeps the driver to it. In another configuration (MBIM, ECM, or with a function switched off) the same number can belong to another function, and then `Start`'s checks are the guard: before anything is opened it refuses an interface whose class, subclass and protocol are not all `0xff` or that does not have exactly the QMI function's three endpoints (one interrupt IN, one bulk IN, one bulk OUT), with a log line that says which (`RMNet: not the QMI interface: interface <n> has class <c> subclass <s> protocol <p>, not ff ff ff`, or `... has <k> endpoints (<i> interrupt in, <b> bulk in, <o> bulk out), not 3 (one of each)`). That is the rule of the Linux kernel's `qmi_wwan` for these modems, whose DIAG port can have the QMI function's class, subclass and protocol but has two endpoints. On the RM520N-GL interface 4 has exactly those (the I/O registry gives `bNumEndpoints` 3 with class, subclass and protocol 255, and the harness captures in `tests/fixtures/capture-*.txt` record bulk in `0x8e`, bulk out `0x0f` and interrupt `0x88`), so its path is unchanged.

The driver has run only on the RM520N-GL; **the other models are untested**. All are Quectel (vendor `0x2c7c`) entries of the Linux kernel's `drivers/net/usb/qmi_wwan.c` (torvalds/linux, `master`, fetched 2026-11-15 from `https://raw.githubusercontent.com/torvalds/linux/master/drivers/net/usb/qmi_wwan.c`). Five entries name the interface number. The kernel matches the others by class only (`QMI_MATCH_FF_FF_FF`), and their number comes from Quectel's *UMTS_LTE_5G Linux USB Driver User Guide* (version 3.0, 2022-03-18, Table 1, which gives interface 4, the `qmi_wwan_q` network adapter after `AT+QCFG="usbnet",0`, with DIAG on 0, GNSS on 1, AT commands on 2 and the modem port on 3) or from the kernel commit that added the model. The same list is in `scripts/check-personalities.sh` (which checks each personality against it) and in `quectelModels` in `app/StatusModel.swift` (which `RMNet status` uses), and `make script-test` checks that the plist and the two lists agree.

Why the kernel matches most of them by class rather than by number: on these modems the functions' interface numbers follow the USB configuration the modem is set to, and the QMI function is told from the DIAG function by its endpoints. On the RM500Q-GL, EM160R-GL, EM060K, RG650V and RG660QB the DIAG function has protocol `0x30` (`ff/ff/30`, in `drivers/usb/serial/option.c` and the RG650V's listing), so class, subclass and protocol alone tell them apart; on the EC25, EP06 and EM12 the DIAG function is `ff/ff/ff` like the QMI function, with two endpoints instead of three (`option.c` binds their `ff/ff/ff` interfaces only with two endpoints, `NUMEP2`). `Start`'s endpoint check covers both.

**Not matched.** The RG255C (`2c7c:0316`, `{QMI_QUIRK_SET_DTR(0x2c7c, 0x0316, 3)}, /* Quectel RG255C */`): its QMI interface 3 has class, subclass and protocol `ff/ff/50` (the `usb-devices` listing in kernel commit `5c964c8a97c1`, "net: usb: qmi_wwan: add Quectel RG255C", 2024-12-16), and `Start` takes only `ff/ff/ff`, so a personality for it would always be refused. The kernel's EC20 entry under Qualcomm's vendor ID (`{QMI_FIXED_INTF(0x05c6, 0x9215, 4)}`) is not a Quectel-vendor entry and is not matched either. Every Quectel entry of `qmi_wwan.c` is otherwise in the table.

What an untested model may meet:

- Core asks every model for the RM520N-GL's data format (raw IP, QMAP both ways, up to 31,744 bytes down and 16,384 up) and needs the answer to be usable (`data_format_usable`: raw IP, QMAP both ways, at least one datagram each way, and aggregation sizes from 2,048 bytes up to the sizes asked for). Neither source states a per-model limit, so Core's data format is unchanged; a modem that refuses QMAP or reports no uplink aggregation would keep its session in backoff and never bring the link up.
- The driver sets DTR on the QMI interface for every model, as the kernel does for the entries marked `QMI_QUIRK_SET_DTR` and `QMI_MATCH_FF_FF_FF`; the BG96's entry (`QMI_FIXED_INTF`) does not ask for it.
- The serial ports (`RMNetSerial`), `RMNet sms` and `RMNet gps` stay on the RM520N-GL only (`2c7c:0801`; interfaces 0, 1 and 3). With only another model attached, `sms` says `The RM520N-GL (USB 2c7c:0801) is not attached.` and `RMNet status` names the model, for example `modem: 2c7c:0800 RM500Q-GL (untested) attached, QMI interface 4 (class, subclass, protocol ff)`. `status` counts a model as in QMI mode only when its own QMI interface number has class, subclass and protocol `0xff` and three endpoints; otherwise it prints `... attached, interface 4 is not a QMI interface (class, subclass, protocol ff, 3 endpoints): not in QMI mode`.

## Harness

`build/rmnet-harness` runs the core against the real modem from userspace, through IOUSBHost.framework. It needs the modem attached in QMI mode (USB `2c7c:0801`; it uses only the QMI interface, the one whose class, subclass and protocol are all `0xff`) and nothing else holding that interface. It needs no root and creates no network interface.

- `rmnet-harness probe [-v]` finds the QMI interface, prints its endpoints and the modem's serial number, and exchanges one QMI CTL Sync. It prints `sync ok` and exits 0, or `sync: no answer` and exits 1 after 10 seconds. `-v` prints every QMI control message as hex, `>>` sent and `<<` received.
- `rmnet-harness connect [-v]` brings a data connection up on profile 1 with the core's connection state machine, prints `link up`, then the IPv4 address with its mask and gateway (`ipv4 none` if that family did not come up), the IPv6 address with its prefix length, the DNS servers and the MTU. It then stops the connection and exits 0. It exits 1 with `no link after 90 s` if the link does not come up. `-v` also prints every QMI message and the granted data format.
- `rmnet-harness ping [-v] [-6] [-c COUNT] ADDRESS` brings the connection up the same way, then sends COUNT ICMP echo requests (default 3), one a second, from the modem's IPv4 address (or IPv6 address with `-6`), framed as QMAP on mux `0x81` over the bulk endpoints. It answers QMAP flow-control commands from the modem and prints `reply from ADDRESS: seq=N time=T ms` for each echo reply that arrives within 2 seconds of its request. Two seconds after the last request it prints `COUNT sent, M received`, stops the connection and exits 0 if M is at least 1, 1 otherwise. It exits 1 at once if the link comes up without an address of the requested family. `-v` also prints every bulk transfer and every QMAP frame that is not a reply.

Both commands stop the connection (WDS Stop Network, then Release Client ID for every client) before exiting, also on Ctrl-C, so nothing is left running on the modem. The network takes a few seconds to finish tearing a connection down: a command started within about a second of the previous one often gets IPv6 but not IPv4 (WDS Start Network for IPv4 fails with call end reason 3GPP 36, regular deactivation). Wait a few seconds between runs.
